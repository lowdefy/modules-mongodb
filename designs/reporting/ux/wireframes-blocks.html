The same six surfaces, drawn in the blocks we actually have.

The UX deck drew what the module should do. This one draws what it is made of: every region labelled with the block behind it, checked against the installed source of @lowdefy/blocks-antd, -basic, -antd-x, -echarts and -aggrid. Almost all of it is config. One block method has to be added, and three places bend away from the drawing — each marked where it happens rather than listed at the end.

Builds as drawn

The rail's recency groups, rename and delete; the results panel with selection; the save sheet; the list, its menus and its empty states; the whole report page. No block change, no workaround.

Config, not code.

Bends

Section reorder becomes ↑ / ↓ rather than a drag handle. The trace line is titled with the tool's name. The list's kebab opens a modal until the grid has a menu cell — the one column plate 4 draws that no cell type covers.

Three, all marked in place.

Blocked

A starter that fills the composer instead of sending it. The sender is uncontrolled and no method writes it — so AgentChat gains setInput, and the welcome moves outside the block entirely.

Build 1 /reporting/chat — first run 1 block change

The welcome is page blocks, not block properties

AgentChat.welcome flattens its prompts into one row and the block has no areas, so a two-track empty state cannot be built inside it. Leave welcome unset — the block then renders nothing in its place — and put the empty state above the chat as ordinary blocks, shown while _state.messages is empty. That buys full layout freedom, and it only works because the starters can fill the composer.

  1. 1Rail search is not a block property — it does not need to be. AgentConversations has no search, but its items come from config, so a Search block above it filtering the array before it reaches the block is the whole feature, and it searches the snippet as well as the title.
  2. 2Recency grouping ships. Each item takes group and timestamp, and the groupable property renders the headings. Group order follows the order the items arrive in (the block's grouping is a plain reduce, with no alphabetical sort), so ordering by recency server-side gives Today → Previous 7 days → Older with nothing else to configure.
  3. 3Rename and delete ship too. A menu array renders the hover ⋯ and onMenuClick fires with the action key and the conversation key — enough to open a rename Modal or call the new soft delete. danger: true colours the delete item.
  4. 4The bend. A tool call renders as a thought-chain row whose title is the raw tool name; only the description is authorable, and it comes from a display string on the tool's output (first 80 characters), with the full markdown — the pipeline — behind the collapse. So the row reads query_data · Read orders · 4,812 rows · 0.4s rather than leading with "Read orders". Accepted: the honest label costs nothing.
  5. 5Mermaid needs no change at all. messageDisplay.renderMermaid defaults true and mermaid 11 ships inside the chat block, so an xychart-beta or pie fence renders as an inline sketch. This is prompt work, not block work.
  6. 6And the ceiling is real. The block classifies only text, reasoning, tool, file and status parts; custom data-* parts are explicitly not rendered inline and the schema has no areas. Markdown and mermaid are the entire in-thread vocabulary — which is why the panel exists.
  7. 7Composer chips send immediately, and that is correct here. suggestions (or a data-suggestions part from the agent) render above the composer and send on click. A follow-up you picked is one you meant; only the first-run starters need editing before sending.
  8. 8The panel scope is a SegmentedSelector writing to state, with each card's visible testing it. Tabs would work too, but the segmented control keeps the counts on one line and matches the list page's scope switcher — one pattern, two surfaces.
  9. 9Selection is a CheckboxSwitch whose id is the state path (results.$.selected), so ticking a card writes into the same array the panel renders from and the footer count is an _array.filter over it. No selection machinery.
  10. 10Save as report opens a Modal by method call, passing the filtered selection through state. The typed path — the agent's tool — opens the same modal, so both routes converge exactly as the UX deck asks.
  11. 11The collapsed rail is hand-rolled: AgentConversations has no collapsed mode, so the strip is a Box of three Buttons shown when the rail is hidden. The antd Splitter block — collapsible, resizable, with an onCollapse event — could carry both edges instead if the two hand-rolled strips start reading as two features rather than one pattern.
  12. 12Collapse state is session-scoped. There is no client-storage action and SetGlobal lives in memory, so the state follows the user between pages and resets on reload. Persisting it costs a document and a write per toggle for a preference that is one click to re-express; the endpoint stays available as a later, additive change.

  1. 1Modal or Drawer, opened by method call from the panel footer and from the agent's tool path. One component, two callers — the sheet has no idea which route opened it, which is what makes "both routes converge" true rather than aspirational.
  2. 2Every field is an input block whose id is its state path, so the payload sent to create-report is the state subtree — no field-by-field mapping, and adding a field to the sheet adds it to the payload.
  3. 3The bend, stated plainly. Arrows are not a downgrade worth a block: the list is two to four rows, and a sortable list block would be new surface owned forever for a gesture used once per report. If a real case argues otherwise, a sortable property on ControlledList is the additive change.
  4. 4The filter rows are a List over catalog-derived candidates — date fields, plus enum fields that have something to populate a dropdown from. The engine already narrows this set the same way at compile time, so the sheet offers exactly what the report will be able to render.
  5. 5The any / all toggle is a SegmentedSelector shown only for array-typed fields, writing match onto the filter section. The engine work behind it is designed and in flight in report-filters; the sheet needs no block it does not have.
  6. 6The visibility row is absent, not disabled, for a user without a publish role — a visible test intersecting _user.roles with the share_roles var. The server checks it again on write, because a hidden control is a courtesy and the match is the authorization.

The cells already there selector, multipleSelector, switch, textInput and paragraphInput cells landed in PR 2201 and are on vite-hono (17c1392b, an ancestor of the branch) and in the experimental build the demo installs — the display grid's cell.type enum lists all of them. Nothing to port. They are not the answer here, though. A selector is an input: the chosen option is written back into the row node and rendered as the cell's value, and it carries clear, search and placeholder affordances. A menu of verbs is not a value.
The cell that is missing A menu cell: an antd Dropdown whose items[] each carry an eventName, with the *Field row-data resolution, hidden / disabled and danger that ButtonsCell already implements. Small, generic, the same shape as PR 2201 — and every list page in this repo will want it. Until then the kebab is one ⋯ button in a buttons cell opening a Modal of actions. A worse popover, not a worse feature, and swapping it later touches one column definition.
  1. 1Every toolbar control is an input writing to state, with one shared CallAPI re-fetch on change. The scope match is the authorization boundary, so it has to be a request parameter — which conveniently makes the whole toolbar one code path.
  2. 2Row click opens the report — onRowClick into a Link, the same wiring every other module list here uses. The ★ and ⋯ cells stop propagation, so they act on the row without opening it.
  3. 3The ★ is a one-button buttons cell. hideTitle leaves the icon alone, and iconField is a row-data path, so filled or outline comes from the row rather than a shared condition. The event carries the row, which is all set-report-favourite needs — and it works on shared reports, because favouriting is a read-side marker.
  4. 4The one column with no cell type. Plate 4's menu holds five owner actions and two for a non-owner — too many to sit inline as buttons, and the grid has no dropdown renderer. The interim is a ⋯ button opening a Modal, with hiddenField on the row's isOwner choosing which actions it lists. The fix is a menu cell upstream; see the cards above.
  5. 5Load more appends — the cursor lives in state, the response concatenates onto the rows already rendered. Pagination exists if numbered pages are ever wanted, but a cursor is what the endpoint returns.
  6. 6Visibility stays a read-only tag, on purpose. A two-option selector cell would work now that the cell exists — and would turn publishing to the whole app into a single mis-click on a list, where the design makes it a named act in the menu. The capability existing is not an argument for using it.

Build 6 /reporting/report?reportId=… page exists declare the types

Compiled server-side, so the block list is a contract

The report page is one Dynamic block resolving a spec the server compiled. Every block, action and operator the compiler can emit must be declared in types — and an undeclared type does not degrade one section, it fails the whole report to the fallback slot. That makes the list below part of the design, not boilerplate.

pages/report.yaml — the types contract

types:
  blocks:
    - Box
    - Title
    - Paragraph
    - Statistic
    - EChart
    - AgGridBalham
    - Selector
    - MultipleSelector
    - DateRangeSelector
    - Button
    - Alert
    - Markdown
  actions:
    - CallAPI
    - SetState
    - DownloadCsv
    - Link          # fix-in-chat
  operators:
    - _state
    - _api
    - _if_none
    - _function
    - _intl
    - _args
Why this list is load-bearing Dynamic resolves the compiled config against these declarations and rejects anything undeclared — failing the entire report to the fallback slot, not the one section that used it. So a compiler change that emits a new block type is not done until the declaration lands with it, in the same commit. MultipleSelector is declared (the multi-select filter work in flight emits it). Link is the one this deck adds, for the owner-only Fix-in-chat on a broken section.
  1. 1Provenance is a Paragraph the compiler emits from the report doc plus the resolve timestamp — "ran just now" is free at resolve time, which is why the list column says Updated and nothing persists a last-run.
  2. 2Continue in chat is a Button with a Link action, present only when the report carries a conversationId and the viewer owns it. Reports made through the agent's tool path have no conversation id, so the affordance is absent rather than broken.
  3. 3The filter tags need no block work. MultipleSelector takes { label, value } options natively and renders the selection as removable tags — so ids bind the $match while labels show, which is exactly what a looked-up option list needs.
  4. 4KPIs are Statistic, one per section, and carry no download: a single number you can already read has nothing to export. Every query-backed section carries its own ⤓ instead — a Button running the section's query and handing it to DownloadCsv, which the compiler already emits for download sections today.
  5. 5Section headings are separate Title blocks because EChart and AgGridBalham both set additionalProperties: false and have no title property. The compiler already does this; it is worth knowing before someone tries to pass one.
  6. 6Formatted columns are a _function cell renderer over _intl.numberFormat, which is why those two operators are declared. Unformatted all-numeric columns are right-aligned rather than formatted — a count lines up beside money without inventing decimals.
  7. 7The two recoveries on a broken section are owner-only, and both write to the spec. They are ordinary Buttons inside the Alert — one navigating to the chat with the report as context, one calling an endpoint to drop the section. The only new requirement is the Link declaration.

One method, and the reason it is worth a patch. Everything the UX deck asks for is config except a starter that fills the composer — and that is not a detail of the empty state, it is the empty state's whole argument. A starter you cannot edit before sending is a demo; a starter that lands in the composer is a prompt the user makes their own, which is the difference between teaching the report path and performing it. setInput is a controlled sender and one registered method, it unblocks the two-track welcome as a side-effect by letting the whole empty state live outside the block, and the package is already patched in this repo for an unrelated fix.

And one cell, which is not this deck's to demand. The grid's missing dropdown is a gap in @lowdefy/blocks-aggrid, not in reporting: contacts, companies, activities and user-admin will all meet it the first time a list row needs more than two actions. It is worth building for that reason rather than this one — and the reports list ships either way, because ⋯ opening a Modal is a smaller compromise than leaving the repo's one list page that is not a grid.
