# Review 1

### 1. The derivation this design rests on is unbuilt, and the design never decides where the pipeline gets constructed

The "What report-filters already settled" section lists **the derivation rule (three catalog inputs → an `optionsQuery`)** among the things report-filters _shipped_ and this design must not re-decide. It didn't ship as code. report-filters shipped the wire format, the `any`/`all` semantics, and the resolution path — all verified present (`plugins/modules-mongodb-plugins/src/analytics/compileReport.js`, `querySections.js`, `validateReportSpec.js`, and `modules/reporting/api/resolve-report.yaml`). But "the derivation rule" lives only in report-filters' _design prose_ ([report-filters `design.md` lines 140–146](../../../report-filters/design.md), "Two authors: the agent writes the pipeline, the sheet derives it") — a described rule, not a function. There is no `deriveOptionsQuery` / `buildOptionsQuery` helper anywhere in `src/analytics/`, and `validateReportSpec` _validates and normalizes_ a supplied `optionsQuery` (re-attaching `valueKey`/`labelKey`, per `validateReportSpec.test.js:620`) — it does not build a pipeline from catalog inputs.

So turning `{ collection, foreignField, labelKey }` into `optionsQuery { collection, pipeline: [$project, $sort], valueKey, labelKey }` is net-new work this design owns, and the design glosses it as the sheet "emits `optionsQuery`" (proposed picker, bullet 3) without deciding **where that construction happens**. The only two homes are:

- **In the sheet, in Lowdefy config.** The pipeline needs `{$project: {[labelKey]: 1, [foreignField]: 1}}` and `{$sort: {[labelKey]: 1}}` — field-name keys built from runtime selections. That is precisely the pattern `CLAUDE.md` warns off ("Static branches over dynamic keys — prefer static per-case branches with hardcoded paths over dynamically constructing MongoDB dot-notation keys at runtime"). report-filters itself flags the awkwardness: "a sheet cannot author an aggregation pipeline. It does not have to."
- **On the server**, where `create-report` (or a shared helper beside `validateReportSpec`) takes the leaf inputs and produces the one canonical pipeline shape. This is the "one correct way" option: a single place turns inputs into the pipeline that validation and resolution already expect, so a config-built pipeline can't silently drift from `querySections`/`compileReport`.

**Proposed fix:** state plainly that the derivation is unbuilt and is this design's to build, and decide its home — leaning server-side (the sheet posts `field` + the picked label field; `create-report` derives the `optionsQuery`). This is arguably the central decision of the sub-design; right now it's assumed away.

> **Resolved.** Derivation runs **server-side in `create-report`**, not in the sheet. The intro no longer claims report-filters shipped the derivation rule (it shipped the wire format, semantics, and resolution; the rule was prose only), and a new "The derivation runs server-side" decision records it: the sheet posts `{ field, labelKey }`, `create-report` derives the `optionsQuery` from the catalog it already holds, then validates as it already does. The agent route keeps authoring full pipelines; derivation is a pre-validation step that fires only for a filter section with `field` + `labelKey` and no `optionsQuery`. Keeps the sheet a plain form and gives the pipeline shape one owner.

### 2. Preview (open question 4) is under-scoped — "resolve and show the options" is a new endpoint, not a UI choice

Question 4 frames preview as blind-emit (simpler) versus resolve-and-show (a user can catch a mis-picked label field before saving), as if it were a toggle inside the sheet. Resolving options at authoring time needs a backend path that does not exist. `resolve-report` (`modules/reporting/api/resolve-report.yaml:1`) resolves a **stored** report by `report_id` with the _viewing_ user's roles — it runs sections off a persisted spec. There is no endpoint that takes an in-progress, sheet-derived `optionsQuery` and runs it. So "resolve and show the options" means a new authoring-time endpoint that executes a client-influenced aggregation in the author's session — its own auth gate, its own `validateReportSpec`/`querySections` invocation outside the stored-report path, its own 500-cap and failure handling (which then partly answers question 5 too).

**Proposed fix:** either fold preview into question 1's derivation decision and name the endpoint as scope, or defer preview explicitly (blind emit first, options appear at report open) and record _why_, so the cost isn't discovered at implementation time.

> **Resolved.** Deferred — **blind emit, no authoring-time preview.** Options resolve at report open like any agent-authored filter; a preview endpoint (derive + run against the DB from the sheet, with its own auth/cap/failure handling) waits until the wrong-label mistake proves painful in real use. Question 4 now records the decision, and it collapses most of question 5: with no authoring-time query run there is no authoring-time failure to render.

### 3. Open question 3 largely dissolves against shipped code — there is no proposed-filter producer on this route, and the sections list can't host filter rows

Question 3 asks how "proposed" and "user-added" filters coexist in "the same `ControlledList` as the sections," and whether a proposal arrives pre-derived. Both halves are answerable now from what shipped in save-as-report (PR #162), which narrows this from an open question to a mostly-settled one:

- **No proposed filters reach this sheet.** The tick-and-save route feeds the sheet from `get-conversation-results` — which returns only `data-report-chart` / `data-report-table` / `data-report-download` parts (`modules/reporting/api/get-conversation-results.yaml:56–90`) — assembled by `save_as_report.yaml`, which reads the `charts`/`tables`/`downloads` state arrays only. The agent _does_ author filter sections, but on the **generate_report** route, writing them straight into the report spec (`modules/reporting/agents/reporting-assistant.yaml:156,173`), not as a tickable client part. So on the tick-and-save route the picker is **add-only** — there are no assistant proposals to coexist with — unless this design intends to add a filter-proposal part, which would be unstated new scope on the very route report-filters split this work away from.
- **The sections `ControlledList` can't double as the filter list.** Its row is `{ label, type }` plus move-up/move-down/remove (`modules/reporting/pages/chat/components/save_report_sheet.yaml:130–214`). A filter row is a different, richer shape: a field `Selector`, a control, a conditional label-field `Selector`, an `any`/`all` toggle, and a tag preview. "Same `ControlledList` as the sections" would force two unlike row shapes into one list; the filter picker wants its own region — which is exactly what save-as-report reserved.

**Proposed fix:** resolve question 3 to "add-only picker in its own reserved region," and if assistant-proposed filters on this route are actually wanted, raise that as a separate scope decision (a new filter part + emit path) rather than an implementation detail of the picker.

> **Resolved.** **Add-only picker in its own reserved region.** Confirmed with the author: no agent-proposed filters flow into this sheet, and none will be added on spec. Question 3 records it, the "Proposed picker" intro no longer says the user "reads the assistant's proposed filters," and the filter region is kept separate from the sections `ControlledList` (different row shape). Proposing filters into this sheet stays a separate scope decision if it's ever wanted.
