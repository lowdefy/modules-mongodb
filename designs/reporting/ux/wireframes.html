modules/reporting · UX wireframes · 29 Jul 2026

Ask your data anything. Keep the answers worth keeping.

The reporting module carries two jobs on one surface, and today the second one is invisible — a report only exists if the user happens to type "turn this into a report". These wireframes make both jobs legible: exploration is the default motion, and every result the assistant produces is one click from becoming a saved report.

Explore

Ask a question, read the answer, follow it with another. Charts, tables and exports land in a panel beside the transcript instead of scrolling away.

"Which region grew fastest last quarter?"

Report

Pick the results that answered the question and save them as a report with filters — a page to revisit weekly, not a message to scroll back to.

"Build me a monthly revenue report by channel."

Revisit

Your reports, plus any published for the whole app. Favourites, search — and re-queried live on open, so a saved report is never a stale screenshot.

"Where's that margin report from last month?"

Ask→ See results→ Save as report→ Revisit & filter

  1. 1Both side panels collapse. The rail folds to an icon strip (new chat, search, expand) and the results panel to a counted strip — so the transcript can run full-width when the user is reading rather than producing. Collapse state persists per user; on a narrow viewport both start collapsed.
  2. 2Chats group by recency (Today / Previous 7 days / Older) with a search field above. Needs an updated timestamp on the conversation doc — list-conversations returns titles only today. Hover reveals a ⋯ for rename and delete, and delete is soft.
  3. 3One collapsed line per tool call — what it read, how many rows, how long. Expanding shows the pipeline. This is the trust surface: the user can always see what the answer was computed from, and it's already streamed as data parts.
  4. 4A sketch, where a sketch helps. The bubble can't host a Lowdefy block, but AgentChat renders markdown and mermaid natively — so a simple shape (one series, ≤6 categories) can be a real inline chart via an xychart-beta or pie fence. It carries mermaid's own theme, square marks and no hover, which is why it stays a sketch: prompt the agent to skip it for anything multi-series or long-labelled and just describe the result.
  5. 5The sketch hands off in prose. No buttons exist inside a bubble either, so the transcript names where the full chart is and the panel scrolls to the newest card. The comparison, the formatting and the hover values live there — one place, not two half-charts.
  6. 6State the read-only guarantee where it reassures, under the composer. It is true by construction — the engine runs on a read-only principal — so say it once, quietly, instead of leaving users to wonder.
  7. 7Panel collapse is the mirror image of the rail's, on the opposite edge, so the two read as one pattern rather than two features. Expanded layout is 232px / fluid / 348px; the middle column holds a ~62ch measure so prose stays readable at any width.
  8. 8Tables are first-class results. Today only charts and downloads stream back, so a tabular answer is stranded in the transcript and can't be reused. Add a data-report-table part.
  9. 9Select results → save as report. The one change that makes the second job real: report creation stops depending on the user guessing a phrase. Selection is the card's only marking affordance — expand, download and ⋯ act on a single result, and nothing on a card competes with the checkbox for "this one matters".

  1. 1Name is pre-filled from the conversation title the agent already generates on turn one, so the fast path is one keystroke: Save.
  2. 2Sections are the selected results, in order, each showing what it came from. Removing one here is cheaper than editing a saved report later — and the shape maps directly onto the report spec the module already persists.
  3. 3The offered fields come from the catalog, and so do the dropdown values. Two rules narrow the list, both already true in the engine: a bound field must exist on the section's base collection (the filter $match is prepended before the rest of the pipeline, so it can't see a post-$group alias), and a select needs an option source — filterOptions() takes the agent's declared options if present, otherwise the field's enum values from the catalog. A date field needs neither and offers a range. So the sheet lists date fields plus cataloged-enum fields, and shows the values inline — a field with nothing to populate a dropdown from is never offered, rather than saved and then found empty. Options are re-resolved from the catalog each time the report is opened, so widening an enum reaches every saved report without editing any of them.
  4. 4Choose one or choose several — the second doesn't exist yet. FILTER_CONTROLS is ["select", "daterange"], the compiler emits a single-value Selector, and the server's op map is { eq, gte, lte } — a default-deny map that throws on anything else. Multi-select needs a multiselect control compiling to MultipleSelector, and an in → $in op whose value is an array. The array value itself needs no new validation: the built $match goes through the same pipeline walk as any stage, which already type-checks the $in operand, caps it at 100 elements, and rejects $-prefixed keys inside literal values. What it can't know is intent — so the one genuinely new check is that an empty array must drop the triple exactly as null does. $in: [] matches nothing, so clearing a multi-select would otherwise blank every section bound to it rather than removing the constraint, and this is the ordinary cleared state: the block always sets an array, never null, so removing the last tag lands on []. Which control a filter uses is the author's call, so the sheet offers it per filter rather than the agent deciding silently.
  5. 5A foreign-key filter needs a lookup, and that does not exist yet. Today a select's options are literal scalars: the validator rejects anything that isn't a string or number, so a value cannot carry a separate label — you would filter on company_id and the dropdown would show raw ids. They're also capped at 50 and frozen into the spec at save time. A company filter needs three additions: an optionsQuery: { collection, pipeline } on the filter section, a small { valueKey, labelKey } contract naming which column is the id and which the display text (the same shape the chart and KPI contracts already use), and { label, value } options accepted through to the Selector, which supports them natively. The query is catalog-validated and role-checked exactly like a section query — a filter must not become a way to read a collection you can't otherwise reach — and it re-runs on open, so a new company appears without touching the report. Labels can be composite (name, or name + id where names collide); that's the labelKey's job, or a $concat in the pipeline. Long lists get showSearch; a set too large for one dropdown is an autocomplete, which is a separate design if a real case appears.
  6. 6A list field can be filtered two ways, and $in is only one of them. Where the field holds an array — tags, categories, assigned users — "choose several" is ambiguous: match documents carrying any of the chosen values, or all of them. Each is a single query operator, and both are already in the engine's $match allowlist. Any is $in, with no array special case: {tags: {$in: [priority, urgent]}} matches a document whose tags array contains either, by the same multikey rule that makes it match a scalar tags equal to either — one op, both field shapes, still index-usable. All is $all, not an $expr: {tags: {$all: [priority, urgent]}} is the entire clause, where {$expr: {$eq: [{$size: {$setIntersection: ["$tags", […]]}}, 2]}} is the same predicate at three costs — it forfeits the index (and this $match is prepended precisely so it can use one), $setIntersection errors the whole aggregation on any document where the field is missing, null, or scalar unless wrapped in an $isArray guard, and it makes buildFilterMatch emit expression trees where it now emits flat {field: {op: value}} clauses. So: two ops, in → $in and all → $all, chosen by a match: any | all on the filter section that defaults to any. The toggle is only offered where the catalog types the field as an array, since that's where the question is real — but it is not validated against the catalog type, because types there are prompt material rather than enforcement, and a wrong one should cost a hidden toggle, not a rejected report. One limitation to write down rather than discover: this filters documents, not array elements. A section that $unwinds the same array and groups by it still shows unselected tags — the leading $match keeps documents having priority or urgent, then the unwind emits every tag those documents carry. Filtering elements would mean inserting the $match after the unwind, which prepend-only cannot express.
  7. 7This control only exists for users who can publish. Reports are private by default; holding any role listed in the share_roles var grants the ability to publish one to the whole app. Without one the row isn't rendered at all, because a disabled toggle teaches a capability the user can't have. Enforced server-side on write, not by hiding the control.
  8. 8Say that reports are live. Users assume "save" means "snapshot". One line prevents the wrong mental model — and the wrong expectation about stale numbers.
  9. 9The typed path still works. "Save this as a report" in the composer opens this same sheet pre-filled, so the conversational and UI routes converge on one confirm step instead of two behaviours.

  1. 1"New report" leads to the chat, with the report track pre-selected. The list is where reports are found; the chat is the only place they're made — and the button says so rather than opening a builder that doesn't exist.
  2. 2Three scopes, one control. Mine is the default and the common case — most users only ever have their own. Shared holds what publishers have released to the app. Favourites spans both. There is no archived scope: the modules in this repo have one retirement act, a soft delete, and adding a second state would mean two ways to retire a report and a scope to explain.
  3. 3Visibility is a column, not a hidden property. In the Mine scope every row is yours, so "created by" would be a column of one repeated name — the useful fact is which of your reports the whole app can see.
  4. 4"Open source chat" reopens the conversation the report came from — the natural way to extend a report is to keep talking. Owner-only, because the conversation belongs to whoever had it. Requires storing conversationId on the report doc.
  5. 5Publishing is its own reversible act, and it has exactly one audience: everyone. This slot reads Unpublish on a shared report and Publish to everyone on a private one — a plain toggle with no other consequence: the report stays in your list, keeps its favourites and its history, only its audience changes. There is no per-person or per-team sharing, and no link-sharing: the states are only me and everyone in the app. The slot is absent for users without a publish role.
  6. 6Delete is the only retirement, and it is soft. It writes a deleted change stamp — who and when, the same idiom every module in this repo uses — and every read filters deleted: null, so a deleted report leaves the Shared scope for everyone without a second unpublish step. Nothing is removed from the collection, so an operator can restore one; there is deliberately no user-facing undelete, because that is the archive feature under another name. The confirm names the blast radius when the report is published.
  7. 7Paged, searchable, sorted server-side. list-reports currently returns everything, unsorted; the toolbar's controls only mean something if the endpoint takes search, scope, sort and a cursor — and applies the ownership match itself.
  8. 8Recovery lives here, deliberately quiet. A footer link, not a fourth tab — deleted reports are recoverable, but recovery isn't part of anyone's daily loop and a peer tab would imply it is. See plate 5.
  9. 9The Shared scope swaps that column for "Published by". Same table, one column different — here the author is the fact that matters, because you can't edit these and may need to ask someone who can.
  10. 10Duplicate is the non-owner's escape hatch. Rather than a request-access dance, copy a shared report into your own and change it freely. The copy is private and yours, and the original is untouched.
  11. 11Non-owners get a two-item menu — favourite and duplicate. No rename, unpublish, delete or continue-in-chat: those need ownership, and the server enforces it on every write rather than trusting the hidden menu item. No export either, for a reason that isn't about permissions — see plate 6.
  12. 12Row is the click target, opening the report; ★ and ⋯ stop propagation. Contents pills come from the spec's section types — a cheap, honest preview of what a report holds without rendering it.

  1. 1The confirm names who else is affected, and only when that's true — deleting a private report is a one-line confirm about your own report. A published report is the outward-facing case, so the wording leads with the consequence rather than asking "are you sure?", which tells the user nothing they didn't already know.
  2. 2It also says what deleting doesn't do. "Delete" over a data tool reads as destructive; the second line is there because the fear it addresses is real and the answer is reassuring. The write is a deleted change stamp on the report spec — the source collections are never written to by this module at all.
  3. 3Recovery is a page, not a scope. Reached from the list's footer link, it holds your own deleted reports and does one thing. Keeping it out of the segmented control matters: three tabs a user picks between daily, and one page they visit twice a year, are different kinds of thing and shouldn't look alike. Server-side this is list-reports with scope: deleted, still matched to the caller — you never see anyone else's deleted reports, including ones that were published to you.
  4. 4The change stamp is the audit trail, so show it. Soft delete already records who and when; a recovery screen that omits it makes the user guess whether they're looking at their own mistake. There is no permanent-delete action here — nothing in this module hard-deletes, and adding a purge button would be the one irreversible act in an otherwise recoverable system.
  5. 5Restore returns a report to private, always. Silently re-publishing something deleted months ago would hand it back to the whole app before anyone re-read the numbers — and the second row shows exactly that case. So restore is a recovery of the report, not of its audience; republishing is one deliberate click afterwards. Reversing this is a one-line change if you'd rather restore be exact.
  6. 6The empty list points at the chat and names the whole loop in two sentences. It's the same dual-purpose message as the chat welcome, from the other end.
  7. 7A zero-result search says what it searched and offers the escapes that actually help — including the other scopes, since a report someone published is easy to miss when the default view is your own.

  1. 1Provenance in one line — who made it, when, and when it last ran. "Ran just now" is the antidote to the stale-screenshot assumption.
  2. 2Continue in chat reopens the source conversation with the report attached as context, so "why is East down?" is a follow-up rather than a fresh start. Owner-only: the conversation is the author's, and nobody else should be reading it.
  3. 3A multi-select reads as tags, and its empty state means "no constraint". Removing the last tag must widen the report back to everything, not narrow it to nothing — the same rule the server needs for an empty $in. Values are the ids the $match binds on; the tags show labels.
  4. 4Say which sections a filter touches. Sections opt in via filterBy, so a filter that visibly moves three of four cards would otherwise read as a bug.
  5. 5Download belongs to a section, not to the report. An export is one query's rows — export-data validates a single { collection, pipeline } and the CSV's headers are that result's row keys. A report holds several sections over different collections and grains, so a report-level "Export" has no answer to "export what?": it would either silently pick one section or invent a multi-sheet format the module has no way to produce. Each query-backed section carries its own ⤓ instead, and a KPI — one number you can already read — carries none. This is also why the list rows have no Export: you open the report and download the section you meant.
  6. 6Every section states its grain and any exclusions its query bakes in. This is the difference between a number and a number you'd send to a customer.
  7. 7Alignment already works this way: formatted columns right-align, and so do unformatted all-numeric ones — counts line up beside money without inventing decimals.
  8. 8A broken section degrades alone. The module already validates each section against its rows at resolve time and contains a failure to one card; the wireframe adds the two recoveries — ask the assistant to fix it, or drop it. Both are owner-only, since both write to the spec.
  9. 9A shared report you don't own is read-plus-copy. Open it, favourite it, download any section, duplicate it — but no edit actions, and their absence rather than a row of disabled buttons. The header names the publisher instead of "created by you", because that's who to ask.
  10. 10A non-owner's broken section names who can fix it and stops there. No "request a fix" button — that would be a notification system nobody asked for. Knowing whose report it is, is the actionable part.

What the block will not do, and what that costs: AgentChat renders only text, reasoning, tool, file and data-status parts — messageParts.js states outright that "custom data-* parts [are] not handled inline", and the schema has no block areas. The visibility model, settled. Reports are private to their author. Holding any role in the share_roles var grants the ability to publish one to the whole app — the same shape an existing app already uses for its saved exports: per-user documents matched on the creator's id, plus a curated set everyone can read. Publishing is binary and reversible: only me or everyone in the app, toggled in one place, with no per-user grants, groups or share links. Everything that writes to a report spec — rename, publish, unpublish, delete, fix-a-section, continue-in-chat — requires ownership; everything that only reads — open, favourite, download a section, duplicate — does not, and duplicate is the non-owner's path to a version they control. Retirement is a single soft delete, per this repo's established idiom, so there is no second retired-but-not-deleted state to reconcile against visibility — recovery is a quiet page over the same deleted marker, and restoring returns a report private.
