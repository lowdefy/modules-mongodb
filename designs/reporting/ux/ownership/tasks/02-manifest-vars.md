# Task 2: Declare `share_roles` and record why `reports_collection` keeps its name

## Context

`modules/reporting/module.lowdefy.yaml` declares the module's vars. Two changes land here, both consumer-facing surface rather than behaviour, which is why they are a leaf task nothing else blocks on.

**`share_roles`** is the only var the whole reporting UX design _requires_. It is a string array naming the roles whose holders may publish a report to the whole app. It is plural because more than one role can legitimately carry the privilege. Unset means the app cannot publish anything new: `set-report-visibility` (task 5) rejects every publish call, no publish control renders anywhere, and in an app that never had the var the Shared scope is empty because nothing was ever shared.

It is **not a retroactive switch** — an app that removes the var after reports were published still has those reports listed and readable, and their owners can still unpublish them, because unpublish falls back to the owner. That asymmetry is task 5's to implement; what belongs here is the `description` telling a consumer so.

**`reports_collection`** defaults to `report_layouts` while this design, the module and every endpoint call them reports. The name is left over from an earlier concept. Renaming the default would silently point an existing app at an empty collection — a real failure in exchange for tidiness — so the var keeps its name and its `description` gains a line saying so, which stops the mismatch being an open question for the next consumer who notices it.

`docs/{module}/reference/vars.md` is **generated** from this manifest by `scripts/gen-var-docs.mjs`. Do not hand-edit it. `pnpm docs:check` runs on every PR and fails on drift.

## Interfaces

- **Produces:** `_module.var: share_roles` — a `string[]`, possibly absent. Task 5 reads it for the publish gate; task 9 sets it on the demo module entry.

## Task

In `modules/reporting/module.lowdefy.yaml`, under `vars:`, add `share_roles` and extend the existing `reports_collection` description. Every var in this manifest carries full `description` / `type` / `default` / `required` — that is what makes `vars.md` generatable.

```yaml
share_roles:
  type: array
  description: >
    User roles whose holders may publish a saved report to the whole app.
    A string array — more than one role can carry the privilege. Checked
    server-side by set-report-visibility, never in the UI: a hidden menu item
    is an affordance, the match in the endpoint is the authorization.

    Publishing and unpublishing are gated differently, deliberately.
    Publishing requires the caller to be the report's owner AND to hold one of
    these roles. Unpublishing requires the caller to be the owner OR to hold
    one of them — so a share_roles holder can retract a report they do not own
    (anyone trusted to decide what the whole app sees is trusted to decide it
    should stop seeing something), and a report stays retractable after its
    author's role is revoked, after the author leaves, or after this var is
    removed. There is no equivalent power to publish, rename, delete or edit
    someone else's report.

    Unset means nothing can be published: every publish call is rejected and
    no publish control renders. It is NOT a retroactive switch — reports
    already shared stay listed and readable, and their owners can still
    unpublish them.
```

Then append to `reports_collection`'s description:

```yaml
reports_collection:
  type: string
  default: report_layouts
  description: >
    Collection name for saved report specs.

    The default is `report_layouts` although the module, this design and every
    endpoint call them reports — the name is left over from an earlier concept
    and is deliberately NOT renamed: changing the default would silently point
    an existing app at an empty collection.
```

Then regenerate the docs:

```bash
pnpm docs:gen
```

## Acceptance Criteria

- `modules/reporting/module.lowdefy.yaml` declares `share_roles` with `type: array` and no `default`, and `reports_collection`'s description records the naming mismatch.
- `docs/reporting/reference/vars.md` is regenerated and lists `share_roles`.
- `pnpm docs:check` passes with no drift.
- `pnpm ldf:b` from `apps/demo` succeeds. An undeclared var read by an endpoint is a build error, so this is the gate that proves the declaration is well-formed before task 5 reads it.

## Notes

- **Do not add the new endpoints to `api:` or `exports:` here.** Each endpoint task registers its own file, because a manifest `_ref` naming a file that does not yet exist breaks the build. That is also why tasks 5–8 are chained rather than parallel.
- `share_roles` has **no `default`** and is not `required`. An app that never sets it is a valid app with publishing switched off — that is the design's stated behaviour, not a misconfiguration to guard against.
