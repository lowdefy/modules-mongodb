# Task 4: Document two-factor enrolment in `user-account`

## Context

Task 3 changed consumer-observable behaviour that a support flow needs to know about, and
`docs/` is the source of truth for consumer-observable authoring and runtime behaviour.
The change that matters most: **replacing the authenticator turns two-factor off** for the
duration of the flow, so an abandoned replacement leaves the account with two-factor off
until the user enrols again. A support agent who does not know that will read the tile's
**Off** as a bug or a lockout.

`docs/user-account/concepts/auth-methods.md` already carries a short
**"Two-factor routing is internal"** section (line ~169) covering sign-in-time routing.
The enrolment side is undocumented.

## Task

Add a **Two-factor enrolment** subsection to
`docs/user-account/concepts/auth-methods.md`, beside the existing "Two-factor routing is
internal" section. Match the file's voice — short declarative paragraphs, no YAML dumps,
consumer-observable behaviour only.

Cover three facts:

1. **Enrolment is password-gated.** BetterAuth requires the account password to issue a
   new authenticator secret, so the flow collects it before showing a QR code.
2. **Backup codes are shown once and are not re-fetchable.** They are returned alongside
   the TOTP URI at enable time and rendered in the final step; nothing in the module
   fetches them again. Dismissing that step discards them.
3. **Replacing the authenticator turns two-factor off, rotates the secret, and
   invalidates the previous device.** Two-factor comes back on when the user confirms a
   code from the new authenticator. **An abandoned replacement leaves the account with
   two-factor off until the user enrols again** — the account is still reachable with the
   password alone, and the security tile shows **Off**.

Write to what **actually ships**. Do **not** document a way to get fresh backup codes
without touching the authenticator — that is the `codes_only` branch in
the [backup-codes-rotation design](../../../backup-codes-rotation/design.md), blocked on an upstream
action, and that design amends this section when it lands. Until then the only route
to fresh codes is re-enrolment, and the docs should say so plainly.

Front-matter: the file already has a valid block. If you add a genuinely new key concept,
extend its `concepts:` list — `two-factor` is already there, so most likely nothing
changes.

Then regenerate and check:

```
pnpm docs:gen     # regenerates docs/llms.txt and every reference/vars.md
pnpm docs:check   # what CI runs; fails on drift or invalid front-matter
```

`pnpm docs:gen` will pick up the new section in `docs/llms.txt`. No module manifest var
changed in this design, so no `reference/vars.md` should move — if one does, something
else is out of date and is worth a look before committing.

## Acceptance Criteria

- The section makes no claim about regenerating backup codes independently of the
  authenticator.
- `pnpm docs:check` passes.
- `docs/llms.txt` is regenerated and committed if it changed.
